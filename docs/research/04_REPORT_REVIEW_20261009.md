# 深度研究报告审查与路线调整建议

日期：2026-10-09。状态：研究审查；建议尚未经过本项目运行验收。本文记录路线选择依据，不表示已经实现或部署。

## 结论

采纳报告的主要方向：PX4 保留状态估计、速度以下控制和飞控失效处理；上位机先用传统视觉定位与有界速度控制完成目标接近和保持；首个学习任务优先解决感知中已被实验确认的缺口。PPO、Isaac↔PX4 运行时桥接、完整 VIO/SLAM 均由具体需求触发。

相较此前设计，这更符合用户降低学习、集成和返工成本的目标。此前把 PPO 和自定义联仿基础设施排得过早。已有 Windows Isaac 环境继续保留，但不能以已有安装作为必须围绕 Isaac 构建系统的理由。

这是有成熟组成部分支撑的工程路线，不是已经找到可直接部署到当前微型机的完整开源产品。对体系方向可以较有信心，对这套具体硬件能否满足任务仍需证据。

## 需要更正或收紧的结论

### 1. SIGN 已公开代码，但仍不是 Pi 5 上的即用方案

报告中的“代码待接收后公开”已不适用于本轮看到的作者仓库。官方仓库已有源码、ckpt 目录、部署入口及训练/评估说明，因此不能继续以未开源作为淘汰理由。公开仓库不等于复现通过。[作者仓库](https://github.com/Zichen-Yan/SIGN)

论文实机实验把图像通过 Wi-Fi 发给 RTX 3060 笔记本推理，机载 VIO 提供参考跟踪所需的速度和姿态；这不能证明本项目 Pi 5 可以承担同样的全链处理。它适合作为速度层学习导航的后续参考，不宜成为首阶段依赖。[原论文实机配置](https://arxiv.org/html/2508.12394v1)

### 2. 首个学习任务也不应无条件固定为检测器

若任务允许标记且传统方法足够稳定，第一版可以不需要神经网络。先取得传统感知的失败记录，再决定学习模块负责检测、关键点还是其他部分。PULP-Frontnet 支撑微型机上学习感知的可行方向，不能证明其人体目标、镜头和低分辨率设置适用于本项目目标。[作者项目](https://github.com/idsia-robotics/pulp-frontnet)

在选择输入分辨率之前，明确实际目标尺寸、最远识别距离、视场、姿态、光照和运动模糊，并估算目标占据的像素。过早套用 80×48 或 160×96 可能直接丢失任务信息。

检测框本身不能普遍提供完整米制相对位姿。PnP 路线需要已知目标几何、可靠二维与三维点对应和相机标定；双目路线需要有效视差及同步。置信度必须结合几何误差、数据年龄和失锁状态，不能直接把网络分数当位置精度。

### 3. Offboard 失效处理需要审查真实发送行为

MAVSDK 官方文档说明它自动以 20 Hz 重发 setpoint。停止生成新指令不会自动使重发停止，不能据此保证 PX4 会进入 Offboard-loss 处理。`stop()` 会请求 Hold；Hold 的适用条件也需要在目标固件和估计器状态下验证。[MAVSDK 官方接口](https://mavsdk.mavlink.io/main/en/cpp/guide/offboard.html)

此外，`set_velocity_ned` 的第四个量为偏航角，`set_velocity_body` 的第四个量为偏航角速度。不能把“三轴速度＋偏航角速度”随意映射到任一 API。必须锁定消息、坐标系、单位和 yaw 语义，再验证正负方向。

20 Hz、150 ms TTL、0.5 s 等目前只是候选参数。验收要分别覆盖视觉过期、上位控制停更、网关卡死、通信断开、估计器失效和模式切换。PX4 保留底层不意味着所有上层故障都会自动得到合适处理。

### 4. 光流稳速、目标相对定位、返库导航必须分开验收

光流与测距可作为局部速度估计的组成部分，不能直接证明长期全局位置或可靠返库。目标相对定位只解决看见目标时的相对关系。返库还需要回答看不见库位时如何导航、漂移上限如何约束、重新捕获范围是否足够。

可以暂缓搭建完整 VIO，但不能暂缓定义任务需要的定位能力。默认带 GPS 的 SITL 成功也不能作为无 GPS 实机任务的通过证据。

### 5. 工具版本与板卡支持要具体到组合

Pegasus 安装文档的测试组合是 Isaac Sim 5.1.0、Ubuntu 22.04 和开发时 PX4 v1.14.3，明确 Windows 未测试。暂缓引入 Pegasus 有依据；不能据此断言其他组合一定失败。[官方安装文档](https://pegasussimulator.github.io/PegasusSimulator/source/setup/installation.html)

PX4 当前发布页可以找到 v1.17.0，但“最新稳定版”不等于当前 45A AIO 板卡的已验收固件。需要硬件修订、精确 target、固件提交与参数快照，不用同系列 35A 板的资料代替本板证明。[PX4 发布](https://github.com/PX4/PX4-Autopilot/releases/tag/v1.17.0)

报告列出的 BDShot 问题值得进入板卡验证清单，但 issue 关闭、评论提到修复、修复进入某个发布版是不同证据。本轮不宣称选定固件已包含且已验证修复。[相关原始问题](https://github.com/PX4/PX4-Autopilot/issues/26748)

## 决定路线前必须补齐的四组证据

| 证据组 | 必须得到的结论 | 低成本的第一步 | 何时需要改路线 |
| --- | --- | --- | --- |
| 任务与可见性 | 目标是什么、能否加标记、接近距离、遮挡、返库路线与规则限制 | 整理规则原文、目标图片/尺寸、场地图；计算目标像素预算 | 标记禁止、目标太小或不持续可见时调整感知与导航 |
| 质量与能源 | 完整器件能否落在质量/外廓内，供电是否支持计算和飞行 | BOM 质量与功耗预算，登记每项来源和余量 | Pi、相机、散热、供电或结构占用超出余量时调整硬件 |
| PX4 与定位 | 精确板卡固件组合，以及无 GPS 所需估计状态是否有效 | 先整理板卡版本与固件；SITL 分别测试理想定位和定位失效 | 光流/测距覆盖不了任务时增加定位能力或缩小首任务 |
| 计算与视觉 | 采集到控制的完整延迟、丢帧、温升与模型误差 | 用真实相机录制短片；Pi 离线重放传统视觉，再比较候选模型 | 采集/解码已超预算时先改相机流水线，不直接换网络 |

树莓派供电规格与推理 FPS 不能替代机上实测功率和全链延迟。整机质量、推力和能源是架构前置条件，不应排到模型训练之后才发现不可行。

## 调整后的阶段顺序

1. **需求和预算闭合**：把以上缺口登记为可回答的问题，优先关闭会推翻架构的项。未知值保留未知，不将参考 160 g 当实测。
2. **最小 PX4 闭环**：盘点 Windows/WSL 与工具链，锁定一套 PX4 SITL 配置，验证速度接口、坐标变换、状态机与故障路径。可先用 SIH 做无视觉的接口测试，再按需要加入 Gazebo；不同时建设多个完整仿真栈。
3. **传统感知基线**：已知目标几何/允许的标记 → 相对定位 → 有界速度控制 → 到达保持；仿真真值单列为对照，不进入部署接口。
4. **真实视觉与 Pi 重放**：先验证标定、像素预算、几何定位和端到端时延。按场景/录制段划分训练和测试，避免相邻帧泄漏；记录丢失与错误识别的行为。
5. **按缺口加入监督学习**：保持感知接口和控制器不变，比较传统方案与模型在同一保留测试集上的表现。Isaac 按数据缺口提供合成数据，合成性能不能代替真实验收。
6. **无 GPS 与实机逐级验证**：先验证状态估计与基础速度控制，再验证目标任务；阶段安排不代表现在执行刷写、解锁或飞行。
7. **扩展任务与可选 RL**：只有传统控制/规划出现明确、可复现且与感知无关的不足时，再选择 RL 或其他方法，要求同等观测和预算下胜过基线。

2 秒保持可以作为早期冒烟检查，不能代替项目规则快照中至少 10 秒悬停的要求；具体误差、容差和成功条件仍需规则及任务确认。报告中的天数和 95% 等数字只能作为估计/候选门限，不视为承诺或已接受标准。

## 架构与目录的处理

优先稳定语义边界：相机帧及时间戳、目标观测及坐标系/质量状态、导航估计及有效性、速度命令及有效期、模式/故障状态、实验记录。目标观测应能表达二维检测、几何相对位姿和无效观测，不能提前固定为旧设计的 27 维 RL 向量。

控制路径建议为：相机 → 可替换感知器 → 几何/相对定位 → 任务状态机与传统控制 → 指令限幅和过期处理 → 单一 Offboard 发送端 → PX4。导航状态独立提供给任务和控制模块；日志贯穿全链。

训练与部署通过数据格式、标定、模型及预处理配置交接。相同接口有助于替换模块，但不自动保证两个仿真器的时间、动力学和图像一致。

保留现有工作区、资料快照和可工作的 Isaac 环境。报告审查当时design/01–06与ADR-001尚未改写；其后持续规划已同步为v1.0，当前入口见[总纲](../../PROJECT_PLAN.md)。旧设计保存历史区，PPO首任务与必须联仿安排不再作为实施要求。规划验收已完成，实施阶段仍NOT RUN。

下一份实施方案应围绕“需求/预算闭合＋最小 PX4 传统闭环”重写，按已掌握的证据锁定具体版本和接口。先减少会推翻路线的不确定性，再扩大实现范围。
