# 1. 项目目标与系统边界

## 1.1 项目目标

研发一套面向 RMUC 2027 的小型全包围自主空中机器人系统。

系统应具备：

1.  从机库自主起飞。
2.  在已知赛场几何先验下完成区域级导航。
3.  使用前视视觉识别目标和动态实体。
4.  使用短时光流和飞控状态估计辅助局部运动控制。
5.  使用前向多区 ToF 提供近场障碍物距离信息。
6.  接近任务目标时切换到目标相对视觉控制。
7.  根据任务类型执行撞击、拦截、遮挡或信息获取等任务。
8.  碰撞后立即废弃旧位置参考，进入视觉重新获取方位流程。
9.  根据重新获取的视觉信息决定安全退出、返库或任务终止。
10. 自主返回机库并完成停靠。
11. 停靠后通过物理触点与机库通信，上传任务数据并执行允许的补能流程。
12. 支持红蓝阵营配置切换。
13. 通过 Isaac Sim / Isaac Lab、真实传感器测试和分级实机验证完成
    Sim-to-Real。

## 1.2 系统边界

本项目不是单独的一架四旋翼，而是一个由以下子系统组成的自主空中系统：

``` text
RMUC 2027 Rules / Mission Constraints
                  |
                  v
          Hangar System
                  |
        Dock / Data / Energy
                  |
                  v
        Autonomous UAV System
        |          |          |
        v          v          v
      PX4      RK3576      Sensors
        |          |
        |          v
        |     Perception
        |     Mission Manager
        |     RL Skill Policy
        |     Recovery Manager
        |     Safety Supervisor
        |          |
        +----------+
                  |
                  v
             Real Flight
```

系统分成四个故障域：

-   **飞行控制域：** PX4、IMU、姿态/角速度控制、控制分配、电调。
-   **任务计算域：** RK3576、视觉、任务规划、强化学习、数据记录。
-   **机库域：** 触点接口、数据管理、补能管理、无人机状态管理。
-   **独立安全域：**
    规则要求的紧急停桨遥控器/接收机、安全员操作和必要的硬件安全链路。

任务计算域故障不得直接破坏飞控硬实时控制；机库触点或机库控制器故障不得反向破坏无人机飞行电源和飞控；普通
RL Policy 不得覆盖独立安全机制。

### 2.2.1 电池能量计算

待核验的答疑口径为按标称电压计算；以下按该候选口径复算，不构成官方合规结论。

当前已购买电池为 3S 350mAh。具体化学体系和铭牌标称电压应从实物确认。

若为普通 LiPo，按 3.7V/cell 计算：

\[ V_{\mathrm{nom}}=3\times3.7=11.1 \mathrm{V}
\]

\[
E_{\mathrm{nom}}=11.1\times0.35=3.885 \mathrm{Wh}
\]

若为 LiHV，按 3.8V/cell 计算：

\[ V_{\mathrm{nom}}=3\times3.8=11.4 \mathrm{V}
\]

\[
E_{\mathrm{nom}}=11.4\times0.35=3.99 \mathrm{Wh}
\]

因此：

-   电池容量与串数已锁定为 3S 350mAh。
-   化学体系、铭牌标称电压、标称容量和准确型号需要写入 BOM。
-   如果是 3S LiHV，计算结果 3.99Wh，距离 4Wh 上限仅有
    0.01Wh，必须在最终检录前取得明确合规确认。
-   无人机内部所有电池都需要计入总供电容量；不能通过额外增加一块小型备用电池绕开限制。
-   不得把电容组或超级电容直接加入当前供电架构，除非最新正式规则及官方答疑明确允许该具体实现。

### 4.2.4 VL53L8CX

职责：

-   前向 8×8 多区近场距离感知。
-   飞行路径局部障碍物检查。
-   目标接近阶段的距离辅助。
-   近场安全层输入。

限制：

-   8×8 数据不是完整稠密深度图。
-   多区测距更新频率、无效 Zone、材料反射率和环境光会影响结果。
-   不能把标称最远测距范围视为所有障碍物都能稳定检测的距离。
-   不得单独承担高速避障的全部安全职责。

必须建立速度相关的探测距离要求：

\[ d_{\mathrm{safe}} = v\tau+
\frac{v^2}{2a_{\mathrm{brake}}} +d_{\mathrm{margin}} \]

其中：

-   (v)：当前飞行速度。
-   (\tau)：采集、处理、决策和执行总延迟。
-   (a_{\mathrm{brake}})：实测有效减速度。
-   (d_{\mathrm{margin}})：工程安全余量。

如果实际有效探测距离不足以覆盖制动距离，应降低允许速度，而不是依赖 RL
自行弥补。

## 5.1 当前电源架构

``` text
3S 350mAh Battery
        |
        +----------------------> ESC / Motors
        |
        +----------------------> Regulated Logic Power
                                  |
                                  +--> RK3576

                                  +--> Dock Interface Logic
```

具体电压轨、稳压器型号、峰值电流和滤波方案以实测为准。

## 5.2 电源设计要求

1.  推进动力电源和计算/视觉逻辑电源应进行合理隔离与滤波。
2.  RK3576 在电机大电流瞬态下不得出现反复掉电或重启。
3.  相机和 ToF 供电不得因电机噪声产生持续数据异常。
4.  记录电池电压、电流、累计消耗能量和温度。
5.  记录 RK3576 输入电压、5V 轨电压及瞬态跌落。
6.  评估电机启动、加速、接触冲击和急剧姿态调整时的电压下陷。
7.  所有电源保护不得依赖 Linux 正常运行。
8.  充电电路与飞行供电路径必须有明确的隔离和互锁。

### 5.2.1 整机重量、推进和供电可行性门（BB22:G0.5）

当前电机/桨/AIO 和电池属于保留基线，不表示组合已经在 3S 下验证。自由飞行前必须核对器件额定电压/电流与厂商资料，并用推力台验证实际组合；没有证据不能按旧电池日志外推。

称量飞行状态的电池、RK3576 核心板及载板、散热、电源转换、线束、双相机、ToF、光流、急停接收机、规则灯组和护罩；记录整机质量、重心、安装包络、悬停油门、推力余量、持续/峰值电流、温升、压降及最低任务电压下的状态。规则尺寸/质量限制仍需原文核验。

G0.5 的门槛在测试前按额定值、任务剖面和风险冻结；不预填没有依据的推重比。重量、推进或逻辑电源不能闭合时，禁止自由飞行和比赛放行，并限制后续昂贵训练投入；可继续进行隔离的合同、仿真和板端测量。不得为满足 LOCKED 而绕过物理边界。

``` python
battery_state = {

    "cell_voltage_v": None,       # 若硬件支持逐节监测
```

## 5.4 任务能源预算

任务开始前计算：

\[ E_{\mathrm{mission}} = E_{\mathrm{takeoff}} +
E_{\mathrm{navigation}} + E_{\mathrm{approach}} +
E_{\mathrm{interaction}} + E_{\mathrm{recovery}} +
E_{\mathrm{return}} + E_{\mathrm{docking}} \]

仅当：

\[ E_{\mathrm{remaining}} >
E_{\mathrm{mission}}+E_{\mathrm{reserve}} \]

才允许进入任务。

能源余量阈值通过真实飞行数据确定，不在当前阶段凭经验填写固定数值。

### 5.4.1 历史验证飞行数据（仅作参考，不代表 350mAh 新电池表现）

  飞行时长              53.36s
  消耗能量              1.64Wh
  消耗电量            168.8mAh
  平均电流              11.39A
  平均功率           约 110.5W

新电池必须重新完成： - 静态电压和内阻记录； - 推力台不同油门区间功耗； -

-   数据通信触点。
-   充电功率触点。
-   机库电源管理接口。

# 6. 机库与触点通信架构

## 6.1 设计原则

机库和无人机之间采用物理触点作为停靠状态下的有线通信接口。

通信协议尚未确定，因此软件必须先定义抽象接口，不得将具体 UART、CAN
或其他协议直接耦合进 Mission Manager。

``` text
UAV Dock Contacts
       |
       v
DockLink Abstraction
       |
       +--> Link Detection
       +--> Handshake
       +--> UAV Identity
       +--> Status Exchange
       +--> Task Data Upload
       +--> Flight Log Upload
       +--> Mission Config Download
       +--> Firmware / Parameter Version Check
       +--> Charging Status (if integrated)
```

## 6.2 触点接口的逻辑分层

建议至少区分：

  逻辑通道               用途                                 状态
  ---------------------- ------------------------------------ -------------------------
  Contact Detect         判断无人机是否真正停靠               REQUIRED
  Ground Reference       通信电气参考                         TBD
  Data Link              机库与无人机数据通信                 REQUIRED / Protocol TBD
  Charge Power           如采用触点充电，传输充电功率         OPTIONAL / TBD
  Charge Enable          充电互锁                             OPTIONAL / TBD
  Presence / Interlock   防止未正确停靠时启动充电或数据操作   REQUIRED

数据协议候选可以在需求确定后比较 UART、RS-485、CAN/CAN-FD
或其他适合触点连接的有线接口。当前不锁定具体协议。

协议选型需要比较：

-   触点数量。
-   数据吞吐量。
-   电磁干扰能力。
-   接触电阻变化。
-   热插拔能力。
-   通信距离（仅限机库内部连接）。
-   驱动和调试复杂度。
-   多架无人机管理需求。

规则答疑涉及机库最多装载四架空中机器人，因此软件接口预留多机管理能力。当前开发可以先使用单架无人机闭环，不能为了支持多机而增加当前机载平台的无必要负担。

# 7. 定位、运动估计与区域级导航架构

## 7.1 核心原则

本项目不构建持续运行的完整 VIO/SLAM
主定位系统，也不要求无人机始终拥有高精度全局 XYZ 位姿。

导航分为四个层级：

1.  **飞控姿态估计：** IMU 与 PX4 EKF2，负责飞行器姿态和角速度相关状态。
2.  **短时局部运动参考：** MTF-02P
    光流和测距，提供有限时间窗内的运动参考，不负责全场位置。
3.  **赛场区域级认知：**
    固定地标、建筑轮廓、目标语义和已知地图提供区域与粗略方位。
4.  **目标相对视觉：**
    接近装甲板、引导灯、机库标志等时，直接以图像相对误差进行局部引导。

**区域级定位不是连续全局定位；粗略方位不是可直接用于位置闭环的 XYZ
坐标。**

## 7.2 正常飞行状态估计

``` text
IMU / Barometer
       |
       v
PX4 EKF2
       ^
       |
MTF-02P Flow + Downward Range
       |
       v
Short-term Local Motion State
       |
       v
RK3576 State Interface
```

PX4 对外提供的状态必须同时带有效性标志、时间戳和数据年龄：

-   attitude validity；
-   angular velocity validity；
-   horizontal velocity validity；
-   vertical velocity validity；
-   local position validity；
-   local altitude validity；
-   estimator reset counter；
-   optical flow quality；
-   range validity。

不能因为 PX4 消息中存在数值，就默认该状态在控制意义上有效。

## 7.3 光流职责和有效时间窗

MTF-02P 的定位职责限定为：

-   正常飞行阶段短时水平运动参考；
-   局部速度估计辅助；
-   下视距离/高度辅助；
-   低速局部运动和视觉伺服的辅助观测。

光流不承担：

-   全场定位；
-   长时间积分形成可依赖的赛场坐标；
-   地图全局匹配；
-   碰撞后沿用旧速度；
-   碰撞后直接恢复旧位置；
-   单独承担返库导航。

必须区分 `max_flow_sample_age`（单帧新鲜度）、`T_local_reference`（未重锚定的局部运动参考窗口）和 PX4 速度估计有效域。局部窗口由外部参考对比、积分误差与地标间隔共同确定；超过窗口时禁止继续积累导航位移，要求视觉重锚定。持续有新鲜、优质光流并不因飞行累计时长到达窗口就必然使瞬时速度失效；速度是否可用于控制需同时检查 PX4 估计健康、样本年龄和实测误差界。质量下降、地面纹理不足或姿态超域时拒绝相关控制。

## 7.4 赛场区域拓扑图

新增
`ArenaTopologyManager`，以拓扑图代替连续全场定位作为长距离导航的主要任务层接口。

## 7.5 地标接力导航（Landmark-to-Landmark）

长距离移动按多个短段执行：

``` text

       |
       v

       |
       v
检查拓扑边与通行约束
       |
       v

       |

       |
```

每段移动必须有：

-   目标地标；
-   最大运行时间；
-   最大光流积分时间；
-   最大允许视觉误差；
-   最大允许 ToF 风险；
-   失败后的回退动作。

不能把多个短时运动段简单累积为高置信度全场位置。

## 7.6 机库不可见、地标歧义和搜索失败

当机库不可见时：

1.  根据当前区域节点和区域邻接图选择候选地标。
2.  只选择规则允许且图像可观测性经过验证的走廊。
3.  优先移动到可重新识别固定结构的位置，而不是直接朝估计机库方向长距离飞行。
4.  进入短时局部运动窗口。
5.  到达预设时间或视觉边界后停止继续平移。
6.  检查是否捕获候选地标。
7.  地标匹配歧义时保留多假设，不强制选择单一结果。
8.  超时、重复失败或局部运动参考失效时退出当前返库计划。

搜索动作必须是有界的，不得无限盘旋或持续盲飞。

# 8. 碰撞检测、定位失效与碰撞后恢复控制

## 8.1 设计原则

碰撞后必须区分三个不同问题：

1.  **飞控姿态是否仍然可控？**
2.  **垂直高度/下降状态是否仍然可观测？**
3.  **无人机在赛场中的水平位置和方向是否重新可知？**

碰撞前的全局/局部导航位置参考必须作废，但这不意味着 IMU
姿态、角速度、垂直距离传感器和相机必然同时失效。每种状态必须独立重新验收。

碰撞恢复不由普通 Student
决定，也不默认"视觉看见目标后就能恢复速度闭环"。

## 8.2 碰撞前状态必须作废的范围

发生碰撞事件后，至少作废：

-   碰撞前 PX4 Local Position 对任务层的可信度；
-   碰撞前水平速度积分和速度历史；
-   碰撞前地图区域/地图位姿假设；
-   碰撞前目标跟踪轨迹及速度；
-   碰撞前相机---机体外参可信度（若结构可能发生位移）；
-   Student 的 GRU 隐状态；
-   Previous Action；
-   由旧状态生成但尚未执行的动作；
-   所有碰撞前启动、碰撞后才完成的异步推理结果。

PX4 内部 EKF2 是否重置由实际飞控日志和 estimator
状态决定。任务层不能因为 EKF2
仍持续发布数值，就继续把它当作可靠位置来源。

## 8.3 碰撞事件检测

多源检测，不依赖单一阈值：

-   IMU 加速度突变和 jerk；
-   角速度突变；
-   EKF innovation、reset counter 和 health；
-   电机输出饱和或异常；
-   图像瞬时运动；
-   目标跟踪突变；
-   光流质量骤降；
-   下视测距突变；
-   任务是否处于预期接触阶段。

事件检测器输出：

``` python
ImpactEvent = {
    "impact_event_id": None,
    "detected_timestamp": None,
    "estimated_event_time_interval": None,
    "severity_class": None,
    "evidence_flags": [],
    "confidence": None,
    "localization_epoch_before": None,
    "localization_epoch_after": None,
    "control_epoch_before": None,
    "control_epoch_after": None,
}
```

`estimated_event_time_interval`
用于处理碰撞检测存在延迟的情况。对时间区间内采集、但在碰撞后才完成处理的帧，必须保守丢弃。

### 8.4.1 恢复状态持续控制与漂移边界

ATTITUDE_RECOVERY 之后的垂直恢复、视觉获取、搜索和局部视觉阶段，仍必须持续通过姿态/角速度、推力源、执行器和垂直状态健康检查。恢复控制器持续输出新鲜有效的姿态/推力；不能只采图而中断底层控制，也不能在后续状态丢失健康条件后继续偏航或视觉伺服。

本文件“禁止平移/停止平移”在无可靠水平反馈的恢复分支中指撤销主动平移指令，不承诺物理水平速度为零。碰撞惯性和外力仍可能造成漂移；必须以外部参考测量最坏漂移、姿态恢复时间、剩余高度和碰撞净空，冻结恢复包络。无法在包络内退出时进入已验证 failsafe。禁止为满足“禁止平移”而发送缺少估计支持的零速度。

### 8.5.1 重要的 PX4 控制事实

PX4 v1.16 Offboard 文档对 ROS 2 `OffboardControlMode`
的估计状态依赖作了区分：

  控制量            PX4 对应控制层   位置/速度估计要求
  ----------------- ---------------- ---------------------
  Position          位置控制器       需要位置估计
  Velocity          速度控制器       需要速度估计
  Acceleration      更低层控制器     需要速度估计
  Attitude          姿态控制器       不要求位置/速度估计
  Body Rate         角速度控制器     不要求位置/速度估计
  Thrust + Torque   更低层           不要求位置/速度估计

这里的"不要求位置/速度估计"不等于"不需要状态估计"。多旋翼仍然需要有效姿态和角速度反馈，才能使用相应内环。

对于本项目的 MAVLink2 路径，PX4 v1.16 文档列出了多旋翼可用的
`SET_ATTITUDE_TARGET` 姿态+推力或角速度+推力组合；最终可用性必须在
MicoAir743V2-AIO 实际 PX4 固件版本上验证。

参考： - https://docs.px4.io/v1.16/en/flight_modes/offboard -
https://docs.px4.io/v1.16/zh/config/safety

## 8.6 恢复期间的控制方案

### A. 姿态恢复（ATTITUDE_RECOVERY）

目标：停止不可控旋转并恢复可控姿态，不承诺水平位置保持。

前置条件：

-   PX4 姿态四元数有效且新鲜；
-   角速度数据新鲜；
-   `THRUST_SOURCE_VALID=true`，且 thrust source 在碰撞后重新确认；
-   飞控未报告关键 IMU/执行器故障；
-   电机和电调没有明确失效；
-   Companion 与 PX4 控制链路正常。

主候选控制接口为 `SET_ATTITUDE_TARGET` 的 attitude + thrust：

1.  读取碰撞后重新确认有效的姿态四元数；
2.  构造 roll/pitch 回正目标；
3.  仅在当前 yaw 姿态有效时，才以当前 yaw 作为短时朝向保持参考；该 yaw
    不被解释为赛场全局方向；
4.  由恢复控制器生成带 TTL 的 attitude + thrust 动作；
5.  由 PX4 内部姿态/角速度控制器执行内环。

`SET_ATTITUDE_TARGET` 的 body-rate + thrust
可作为经过验证的瞬时角速度阻尼模式，但单纯的零角速度指令不会自动把倾斜机体恢复到水平，因此不能把它当成完整的姿态回正或悬停控制器。

PX4 模式合同：

-   主候选为 PX4 `OFFBOARD` + MAVLink `SET_ATTITUDE_TARGET`；
-   若碰撞发生时 PX4 已处于 Offboard，Recovery Controller
    只有在当前模式仍被确认、且实际固件接受该消息组合时，才切换到新的
    attitude+thrust setpoint 流；
-   若 PX4 已退出 Offboard，必须按"预发送新鲜恢复
    setpoint（满足固件进入前要求）→ 请求模式 → 等待 ACK/实际 nav_state →
    确认控制所有权"的顺序执行；
-   若仍在
    Offboard，必须验证从速度消息切换到姿态消息的连续性；未验证前按不支持无缝切换处理；
-   未确认模式切换前，不得假设 PX4 已经接管恢复动作；
-   模式请求超时或被拒绝时，进入已验证的 failsafe 分支，不恢复发送旧
    velocity setpoint。

控制合同：

-   使用经过验证的姿态设定值；
-   不直接输出电机 PWM/DShot；
-   不使用碰撞前位置；
-   不使用碰撞前速度；
-   不把零水平速度命令当成"悬停"；
-   姿态恢复动作必须有 TTL；
-   若控制器健康状态变差，交给预先配置并验证的 PX4 failsafe。

### B. 垂直恢复（VERTICAL_RECOVERY）

姿态稳定不等于高度稳定。attitude + thrust
控制不会自动提供位置/高度保持。

只有在下列垂直观测经过碰撞后重新验证时，才允许启用垂直闭环：

-   MTF-02P 下视测距新鲜且有效；
-   或飞控高度/气压计状态通过健康检查；
-   必要时用连续测距计算垂直速度；
-   传感器视场未被结构、地面反射或机体姿态遮挡；
-   量程、更新率和延迟满足控制器要求。

垂直恢复控制器采用独立的 range/height outer loop，向 PX4 attitude +
thrust 接口提供推力设定值。其概念结构为：

``` text
Fresh Height / Range
        |
        v
Vertical State Filter
        |
        v
Height Error + Vertical Rate Error
        |
        v
Bounded PI/PD Controller
        |
        v
Normalized Thrust Setpoint
        |
        v
PX4 Attitude Controller
```

控制器需要
anti-windup、推力上下限、变化率限制和传感器失效检测。`hover_thrust`
只能作为经过当前电池、电机和重量条件校准的参数，不能写成跨架次固定常数。控制增益和推力边界必须通过
SITL、HIL、推力台和受控飞行逐级标定。

若高度/垂直动态状态不可信，禁止宣称具备定高或悬停能力，也禁止仅凭"姿态有效"就发送无闭环依据的固定推力。除非另有经过完整验证、覆盖当前重量/电池/故障包线的
thrust fallback profile，否则不得启用 Companion 的 Attitude + Thrust
恢复控制；应进入经过实机验证的 PX4 failsafe 分支。

### C. 粗略方位恢复（COARSE_BEARING_ONLY）

视觉重新获取的第一阶段只输出：

-   可见固定地标；
-   地标位于图像的左/中/右或上/中/下；
-   粗略方向扇区；
-   目标是否可见；
-   多帧一致性；
-   视觉置信度。

仅凭粗略方向允许进行有限的朝向调整，不允许直接生成水平速度或长距离返航指令。

### D. 局部视觉伺服（LOCAL_VISUAL_SERVO）

这是可选的后续能力，不是碰撞后自动启用的默认功能。

必须先通过独立验证：

-   有稳定目标特征；
-   有连续图像反馈；
-   能估计图像特征误差及其时间变化；
-   相机安装状态和相机---机体外参通过碰撞后检查；
-   有局部障碍距离和制动余量；
-   控制延迟和最大姿态角经过验证；
-   仅允许短时、小幅、低速动作；
-   视觉特征丢失时立即停止平移并退回 COARSE_BEARING_ONLY 或 failsafe。

初期采用传统 IBVS：图像特征误差 `e` 和误差变化率 `de/dt`
经标定的视觉伺服映射生成有界的期望 roll/pitch/yaw 动作，再由 PX4
attitude controller 执行。具体符号、增益和相机安装角度必须由标定与
SITL/实机测试确定，不得凭图像左/右方向直接猜测机体运动方向。

优先先实现传统 IBVS（Image-Based Visual Servoing）基线，再评估 RL
是否有必要。粗略方位不等于视觉伺服所需的完整相对运动观测。

## 8.7 PX4 模式和失效分支：不得凭名称推断行为

本项目当前使用 MAVLink2 over UART，PX4 固件准确版本和 commit 尚需冻结。

PX4 v1.16 文档说明：

-   Offboard 通过 MAVLink setpoint 消息流或 ROS 2 `OffboardControlMode`
    维持外部控制存活信号；
-   至少 2Hz 是 Offboard 存活要求，不是本项目的控制频率目标；
-   切入 Offboard 前需先持续发送超过 1 秒；
-   MAVLink 模式下 setpoint 消息同时承担 setpoint 与存活信号；
-   停止消息后，PX4 根据 `COM_OF_LOSS_T` 和 `COM_OBL_RC_ACT`
    执行失联动作。

此外，PX4 v1.16 位置丢失故障保护文档说明：在 PX4
判定当前飞行模式依赖的位置估计丢失时，`COM_POSCTL_NAVL`
会根据是否假定存在 RC 和是否有高度信息选择后续动作；无 RC
且有高度估计时可进入 Descend，无高度估计时可能进入 Flight Termination。

该行为只有在 PX4
自身检测到相应的位置丢失故障、且当前模式/状态满足触发条件时才适用。RK3576
内部递增 `localization_epoch` 并不会自动让 PX4 EKF2
的位置有效标志变为无效。

**这些路径不是同一个 failsafe，也不能简单地认为 Offboard
失联必然等于位置丢失。**

控制权交接时还必须验证消息类型切换：从 `SET_POSITION_TARGET_LOCAL_NED`
速度设定切换为 `SET_ATTITUDE_TARGET` 姿态/推力设定，是否能在当前
Offboard 会话中连续被实际固件接受，必须通过 SITL/HIL
确认。不能仅依据文档中两种消息都受支持，就推断消息类型可以在任意时刻无缝切换。

若当前 Offboard 会话不接受消息类型切换，则按显式模式交接处理： 1.
Recovery Controller 生成新鲜且合法的恢复设定值； 2. 按实际固件要求预发送
setpoint； 3. 请求目标模式； 4. 等待 ACK 和实际 `nav_state`； 5.
超时后进入配置好的 failsafe； 6. 任何阶段都不得继续发送旧 Student
velocity setpoint。

PX4 v1.16 文档要求在进入 Offboard 前先持续发送超过 1 秒的有效 setpoint
流。该要求必须在实际固件上复核。

因此必须在实际固件上分别测试：

1.  Offboard setpoint 停止；
2.  Companion 进程崩溃；
3.  MAVLink UART 断开；
4.  PX4 位置有效标志失效；
5.  速度有效标志失效；
6.  高度有效标志失效；
7.  IMU/姿态估计失效；
8.  无 RC 输入条件；
9.  独立 E-stop 动作。

参数候选：

-   `COM_OF_LOSS_T`
-   `COM_OBL_RC_ACT`
-   `COM_POSCTL_NAVL`
-   `COM_RC_IN_MODE`
-   `COM_RCL_EXCEPT`
-   相关位置/高度估计器和 failsafe 参数

不在文档中预填未经实际固件验证的最终参数值。

## 8.8 碰撞恢复禁止事项

-   不允许继续使用碰撞前 Position Setpoint。
-   不允许把旧 Local Position 当作真实位置。
-   不允许把碰撞前速度积分作为控制反馈。
-   不允许继续沿碰撞前地图路径盲目返航。
-   不允许继续使用碰撞前 GRU 隐状态。
-   不允许重发已过期的 Student 动作。
-   不允许将粗略视觉方位解释为速度估计。
-   不允许把 Attitude + Thrust 解释为自动悬停。
-   不允许在视觉重新获取失败时自动恢复原任务。
-   不允许在没有高度状态时声称已具备受控下降能力。

## 8.9 碰撞恢复专项测试

测试顺序：

1.  仿真中注入碰撞事件；
2.  验证 Epoch 原子递增；
3.  注入碰撞前图像的延迟推理结果；
4.  注入碰撞前动作的延迟发送；
5.  验证所有旧消息被拒绝；
6.  在 SITL 中分别模拟位置、速度、高度状态有效/无效；
7.  验证 Offboard attitude + thrust 路径；
8.  验证垂直测距失效分支；
9.  验证视觉只恢复粗略方位时禁止平移；
10. 验证局部视觉伺服失去特征后的退出；
11. 在 HIL 中验证 PX4 failsafe；
12. 在隔离测试环境中开展受控实机验证。

所有接触测试必须在风险评估、机械保护、隔离区和独立急停措施下开展。

## 9.4 高速目标观测

高速目标的主要难点是：

-   像素尺寸小。
-   曝光时间过长导致运动模糊。
-   目标可能只出现少量帧。
-   相机自身运动会影响轨迹估计。
-   RK3576 推理和后处理有延迟。

建议将前视视觉设置为两个配置档：

  -------------------------------------------------------------------------------------------
  模式             主要任务                      设计要求
  ---------------- ----------------------------- --------------------------------------------
  Normal           场景理解、装甲板和车辆检测    稳定帧率、较低计算开销
  Perception

  Fast Object Mode 飞镖/高速目标候选检测与跟踪   更短曝光、更高采集帧率、降低不必要的后处理
  -------------------------------------------------------------------------------------------

具体帧率由相机模组、CSI 带宽、曝光、ISP 和 RK3576 实测决定。

### 10.4.1 单位和坐标变换

策略层采用 BODY_HEADING_FLU：X 为水平前向，Y 为水平左向，Z
为世界竖直向上。它是随航向旋转的导航机体系，不随 roll/pitch 倾斜；这样
`vz_up` 始终表示世界竖直方向。PX4 的 MAVLink
`SET_POSITION_TARGET_LOCAL_NED` 最终使用 LOCAL_NED 速度设定值。

设 PX4 yaw 为 NED 约定下从 North 顺时针为正的角度，策略层
BODY_HEADING_FLU 线速度转换为：

\[
\begin{bmatrix}
v_N\\
v_E\\
v_D
\end{bmatrix}
=
\begin{bmatrix}
\cos\psi & \sin\psi & 0\\
\sin\psi & -\cos\psi & 0\\
0 & 0 & -1
\end{bmatrix}
\begin{bmatrix}
v_{x,\mathrm{forward}}\\
v_{y,\mathrm{left}}\\
v_{z,\mathrm{up}}
\end{bmatrix}
\]

其中： - (\psi=0) 时，前向为 North、左向为 West； -
(\psi=90^\circ) 时，前向为 East、左向为 North； -
`vz_up` 转换为 NED 的 `v_D=-vz_up`； - 策略层正 yaw rate 定义为绕世界 Up
轴逆时针，转换为 NED yaw-rate 时取负号。

候选消息映射：

``` text
Message: SET_POSITION_TARGET_LOCAL_NED
coordinate_frame: MAV_FRAME_LOCAL_NED
vx, vy, vz: transformed NED velocity
yaw_rate: -yaw_rate_ccw_world_radps
```

`type_mask` 位定义（MAVLink common message）：

      位 名称              当前全轴速度模式
  ------ ----------------- ------------------
       1 X_IGNORE          置位
       2 Y_IGNORE          置位
       4 Z_IGNORE          置位
       8 VX_IGNORE         不置位
      16 VY_IGNORE         不置位
      32 VZ_IGNORE         不置位
      64 AX_IGNORE         置位
     128 AY_IGNORE         置位
     256 AZ_IGNORE         置位
     512 FORCE_SET         不置位
    1024 YAW_IGNORE        置位
    2048 YAW_RATE_IGNORE   不置位

因此，全轴速度 + yaw-rate 的候选掩码为：

\[ 1+2+4+64+128+256+1024=1479 \]

若该动作不控制垂直速度、需忽略 `vz`，候选掩码为：

\[ 1479+32=1511 \]

以上掩码是按 MAVLink 位定义计算的候选合同；必须在实际 PX4 固件和
`SET_POSITION_TARGET_LOCAL_NED` 接收路径中用 SITL/HIL 验证。

### 动作限幅

水平速度采用向量限幅：

\[ v_h=\sqrt{v_x^2+v_y^2} \]

若 (v_h>v_{h,\max})，按比例缩放水平向量，保持方向不变：

\[
\begin{bmatrix}v_x'\\v_y'\end{bmatrix}
= \frac{v_{h,\max}}{v_h}
\begin{bmatrix}v_x\\v_y\end{bmatrix}
\]

另外必须实施： - 垂直速度独立限幅； - yaw-rate 独立限幅； -
水平加速度限制； - 垂直加速度限制； - jerk / setpoint slew-rate 限制； -
ToF 制动距离约束； - 根据 PX4 velocity validity 逐轴拒绝动作。

限幅数值在真实机体辨识和控制测试后冻结，不在本版虚构固定数值。

坐标变换、掩码和正负方向必须通过 SITL 单元测试、HIL
和受控实机低速测试验证，不允许只依靠代码注释确认。

### 10.4.2 控制语义

-   `vx/vy/vz` 表示速度设定值，不是位置、加速度或姿态角。
-   `vx/vy` 使用水平航向对齐 FLU；`vz_up` 使用世界 Up 轴。
-   `yaw_rate_ccw_world` 使用世界 Up 轴，不是绝对偏航角。
-   各轴必须有独立有效性标志。
-   所有输入必须为有限数值，不接受 NaN/Inf。
-   Student 网络原始输出可采用 `tanh` 归一化到 \[-1, 1\]；进入 Action
    Schema 前必须按已冻结的每轴最大值映射为物理单位 m/s、rad/s。
-   Action Schema
    中的速度和角速度字段始终使用物理单位，不使用含义不明确的"归一化速度"。
-   只有 `SET_ATTITUDE_TARGET.thrust` 使用 MAVLink
    定义的归一化推力范围（多旋翼候选 0--1）。
-   限幅、加速度限制、jerk 限制和动作平滑由 Action Validator / Safety
    Supervisor 统一执行。
-   Student 不输出电机 PWM、DShot 或 ESC 电流命令。
-   正常速度动作只有在 PX4 对应速度状态有效时才能发送。
-   `v_xy_valid=false` 时拒绝水平速度动作。
-   `v_z_valid=false` 时不得发送垂直速度字段；仅水平速度 + yaw-rate
    的候选掩码为 `type_mask=1511`，但默认拒绝，放行条件见 10.4.3。
-   `v_xy_valid=true` 且 `v_z_valid=true`、三轴速度均参与控制时使用候选
    `type_mask=1479`。
-   若某轴所需估计无效，该轴必须被屏蔽或整个动作被拒绝，不能用 0
    伪装成闭环有效。

### 10.4.3 部分轴消息与垂直控制完整性

1479 和 1511 的位和计算正确；掩码只选择字段，不能补足缺失估计或生成垂直控制。当前默认仅允许经验证的全轴速度 + yaw-rate 组合。1511 保留为 PROVISIONAL，必须证明实际固件的垂直 setpoint、推力来源与失效行为；未通过前，`v_z_valid=false` 时拒绝整个正常速度动作并交接，不能自动发送 1511。

仅 yaw-rate 的 `SET_POSITION_TARGET_LOCAL_NED` 也不是本项目已支持接口；当位置、速度和加速度全被忽略时，参考 PX4 v1.16.0 接收路径不会发布该类 Offboard 控制模式。速度无效时的有界偏航走经验证的恢复姿态/推力路径。

所有参与控制的值必须有限；忽略字段由 Adapter 按已验证的协议约定编码，不能把内部的“无效”直接作为 NaN 绕过控制合同。水平前/左到 NED 的转换额外要求新鲜有效 yaw；单轴屏蔽后需重新检查旋转得到的 N/E 两轴可用性。正常动作的安全包络还依赖有效高度、障碍与姿态条件，不能仅检查速度数值。

## 10.5 碰撞恢复动作空间

碰撞恢复不复用 `NormalVelocityAction`。

``` python
RecoveryCommand = {
    "schema_version": "2.0",
    "action_type": "ATTITUDE_THRUST",  # or BODY_RATE_THRUST
    "clock_id": None,
    "px4_boot_id": None,
    "sync_generation": None,
    "observation_id": None,
    "input_capture_interval_ns": None,
    "earliest_input_safe_deadline_ns": None,
    "frame": "MAV_FRAME_LOCAL_NED_TO_MAV_FRAME_BODY_FRD",

    # ATTITUDE_THRUST branch:
    # MAVLink quaternion order [w, x, y, z], NED -> body FRD.
    "attitude_quaternion_wxyz": None,

    # BODY_RATE_THRUST branch: body FRD rates in rad/s.
    "body_rates_frd_radps": None,

    # MAVLink SET_ATTITUDE_TARGET collective thrust: candidate [0, 1].
    "thrust_normalized_0_to_1": None,

    # Candidate SET_ATTITUDE_TARGET type_mask:
    # 7 for attitude + thrust (ignore body rates);
    # 128 for body rates + thrust (ignore attitude).
    "mavlink_type_mask": None,
    "height_feedback_source": None,
    "height_feedback_valid": False,
    "thrust_source_id": None,
    "thrust_source_valid": False,

    "system_boot_id": None,
    "mission_epoch": None,
    "localization_epoch": None,
    "control_epoch": None,

    "sequence_id": None,
    "issued_at_monotonic_ns": None,
    "expires_at_monotonic_ns": None,

    "source": "IMPACT_RECOVERY",
}
```

该动作只能由 `ImpactRecoveryManager` / 经验证的 `RecoveryController`
生成。

-   姿态+推力不等于位置保持。
-   没有有效高度反馈时，不得宣称自动定高。
-   没有速度估计时，不允许发送正常 Velocity Offboard 动作。
-   不允许将恢复控制器的固定推力值当作所有电池状态和碰撞状态下的通用悬停值。
-   MAVLink `SET_ATTITUDE_TARGET` 的规范字段为：
-   四元数顺序 `[w, x, y, z]`，表示 `MAV_FRAME_LOCAL_NED` 到
    `MAV_FRAME_BODY_FRD`；
-   body roll/pitch/yaw rates 使用 FRD，单位 rad/s；
-   多旋翼 collective thrust 的 MAVLink 规范归一化范围为 0--1；
-   attitude + thrust 候选 `type_mask=7`（忽略三个 body-rate 字段）；
-   body-rate + thrust 候选 `type_mask=128`（忽略 attitude
    quaternion）。

上述值来自 MAVLink common message 定义；PX4
对该消息的实际接收、掩码解释和推力映射仍必须在项目实际固件上验证。

### 12.2.1 任务调度输入和优先级

Task Planner 不把所有任务决策交给
RL。先执行硬约束过滤，再对可行任务进行优先级排序。

硬约束过滤：

1.  当前规则和任务阶段允许；
2.  目标存在且身份确认；
3.  所需传感器和控制状态有效；
4.  当前区域到目标区域存在可行拓扑路径；
5.  能源预算覆盖任务、退出和返库余量；
6.  当前任务不会违反禁入区、碰撞保护和机体状态约束。

软优先级因素：

-   任务剩余时间；
-   预计任务成功概率；
-   任务收益/比赛优先级；
-   目标当前可观测性；
-   当前无人机能源；
-   预计任务能耗；
-   返库路径风险；
-   其他无人机是否已分配同一目标（仅在规则允许的本地/机库协调范围内）。

如果硬约束不通过，任务直接标记为 `INFEASIBLE`，不得通过提高 RL reward
强行执行。

每个 Skill 必须具有统一生命周期：

``` text
INIT
RUNNING
SUCCESS
FAILED
TIMEOUT
ABORTED
```

## 12.3 任务验证（Task Verification）

任务动作执行不等于任务成功。

例如：

-   无人机完成接近，不等于目标交互已经被规则判定成功；
-   无人机接触目标，不等于任务结果已经确认；
-   无人机进入目标区域，不等于遮挡条件已经建立；
-   无人机降落，不等于已经完成有效机库停靠；
-   数据已经发送，不等于机库已经完整接收。

每个任务必须有独立的成功证据、失败条件、超时和复位流程。

## 12.4 Skill A：Region Navigation

-   识别当前区域；
-   选择下一个可观测地标；
-   查询区域拓扑边；
-   检查通行约束；
-   在短时运动窗口内移动；
-   到达地标后重新识别；
-   置信度不足时停止长距离运动；
-   超时进入有界搜索或任务退出。

## 12.5 Skill B：Target Acquisition

-   识别任务目标；
-   判断目标类别；
-   输出目标相对图像方位；
-   检查目标置信度；
-   判断遮挡和可观测性；
-   确认目标属于当前 TeamConfig 的敌方或任务目标；
-   通过目标验证后进入下一任务阶段。

## 12.6 Skill C：Dynamic Object Tracking / Dart Observation and Interception

-   检测动态目标；
-   连续帧关联；
-   区分目标运动和相机自身运动；
-   估计图像相对运动；
-   输出跟踪置信度；
-   目标丢失后清除过期轨迹；
-   飞镖/高速小目标建立独立数据集和延迟指标；
-   将目标是否可见、相对方位、图像速度和不确定度输出给任务规划器；
-   只在规则允许、目标身份确认、飞行边界和安全余量均通过时，才允许进入拦截类
    Skill。

拦截任务不得把"追踪到目标"当作"可以直接追撞"。必须独立评估目标运动预测、无人机自身运动、交会时间、碰撞风险、目标丢失和退出条件。未经验证的高速追逐动作不得直接交给
RL。

## 12.7 Skill D：Target-relative Approach

-   通过图像误差建立相对方位；
-   接近时逐步降低允许速度；
-   检查前向 ToF 有效区域；
-   依据制动距离和感知延迟检查是否可继续；
-   满足任务条件后才允许进入交互阶段；
-   接触或异常事件发生时立即退出普通 Approach。

## 12.8 Skill E：Rule-approved Interaction

将规则允许的目标交互封装为独立
Skill。项目当前需要预留以下任务类型，但最终是否启用、具体交互边界和成功判据均以最新规则和官方答疑为准。

### E1：敌方前哨站/基地目标交互

-   识别目标类别和敌我关系；
-   根据 TeamConfig 获取当前敌方目标；
-   通过区域拓扑到达目标附近；
-   使用前视视觉和 ToF 完成目标相对接近；
-   采用受限速度和接触状态监测；
-   任务结果通过独立证据确认；
-   接触事件触发后立即进入 Impact Recovery。

### E2：飞镖相关动态目标任务

-   使用独立的高速目标观测和跟踪链；
-   估计图像相对运动和不确定度；
-   评估当前任务是否允许拦截；
-   目标丢失或运动预测不确定时中止；
-   不把飞镖运动预测输出直接转化为无约束追逐指令。

### E3：基地降落/附着与飞镖引导灯遮挡

-   识别基地上允许降落/接触的指定区域；
-   识别引导灯及其遮挡区域；
-   通过前视和下视视觉完成目标相对对准；
-   检查局部障碍、接触几何和机体姿态；
-   以专用 Landing/Attachment Skill 执行受限接近；
-   通过视觉遮挡状态、接触状态和稳定时间判断是否完成；
-   监测是否发生滑移、结构干涉或道具异常；
-   任务失败、接触异常或碰撞时退出并交给 Recovery Manager。

"降落在目标上"与"有效遮挡引导灯"是两个独立判据。不得只凭检测到无人机已经接触基地就认定遮挡任务成功。附着结构、磁吸/机械固定或其他接触方式如涉及额外硬件，必须单独核对规则和结构安全，不在当前架构中默认存在。

### 通用交互约束

-   明确目标类别和交互区域；
-   明确最大接近速度；
-   明确机械结构保护要求；
-   明确接触/遮挡判据；
-   明确异常接触和道具损坏风险；
-   明确交互后状态检查；
-   触发碰撞事件时交给 Impact Recovery；
-   具体任务动作必须由最新规则和答疑确认。

## 12.9 Skill F：Information Collection

-   在规则允许的区域采集目标信息；
-   保存图像、目标 ID、时间戳和任务状态；
-   本地缓存；
-   返库后通过触点上传；
-   机库完成文件/数据完整性校验。

若没有规则允许的飞行期间可见光通信链路，不设计普通 Wi-Fi/蓝牙/UWB
实时数据链。

## 12.10 Skill G：Return / Docking

返库分为两个阶段：

1.  **区域级返库：** 根据 Region Graph 和地标接力到达机库附近区域。
2.  **局部停靠：**
    识别机库标志，使用下视视觉完成相对对准，最终通过触点状态确认停靠。

## 12.11 红蓝阵营切换

### Phase 2.5 的部署划分与复验

“完整 Student”指实际完整运行链，不要求所有算子都在 NPU。固定 RKNN-Toolkit2、Runtime、NPU 驱动、BSP、ONNX opset、网络图与输入形状；通过最小转换试验确认 GRU 和具体导出图的支持，不能从 RK3576 的算力参数推断算子兼容。

允许视觉 Encoder/Head 在 NPU，GRU 或不支持算子在 CPU 的显式划分；必须计入张量搬运、调度和并发延迟，交付划分 manifest 与整链 profiling。失败时先调整划分/结构，再决定训练投入。随机权重只证明结构可运行；最终 G6 必须用真实标定集、训练权重和连续序列重测量化误差与闭环行为。

此门约束大规模训练；小规模 CPU 合同测试、仿真控制响应和传统基线可先做，不必等待全部硬件到齐。Phase 3 数据采集可提前支持代表性输入与量化校准。GRU、共享 Backbone、输入维度或采样调度变化后重新检查 G2.5。

# 16. 时间同步、消息接口与动作生命周期

## 16.1 时间同步

所有传感器、飞控、事件和策略消息必须记录：

-   采集时间；
-   接收时间；
-   处理开始时间；
-   处理完成时间；
-   发布/发送时间；
-   数据年龄；
-   时钟偏移；
-   同步质量。

时间戳统一使用单调时钟域。墙上时钟仅用于日志显示，不用于 TTL 判断。

PX4 boot-time 与 RK3576 monotonic clock
之间建立偏移估计，优先使用经过验证的 MAVLink
TIMESYNC/时间同步机制。偏移估计不可信时，不做跨设备精确时序融合，并将
sync quality 标记为 degraded。

需要区分两个时间用途： - Action TTL 和消息新鲜度判断使用 RK3576
monotonic clock； - MAVLink 消息中的 `time_boot_ms` 使用 PX4 对应的
boot-time 毫秒时间，不得直接把 RK3576 monotonic ns 截断后填入。
`time_boot_ms` 的 uint32 回绕必须使用 wrap-safe 处理。

## 16.2 四级上下文标识

每条异步消息按适用范围携带以下标识：

  -------------------------------------------------------------------------------
  标识                    生命周期                 递增/变化条件
  ----------------------- ------------------------ ------------------------------
  `system_boot_id`        单次 Companion 启动      RK3576 进程/系统重新启动时变化

  `mission_epoch`         单次任务/架次            新架次、任务上下文重置

  `localization_epoch`    单次定位参考生命周期     碰撞、定位重置、明确定位失效

  `control_epoch`         单次控制所有权生命周期   Student/Recovery/Safety/PX4
                                                   Failsafe 交接
  -------------------------------------------------------------------------------

不是每条消息都需要所有状态字段参与语义，但消息必须携带完整
header，以便消费者做一致性检查。

## 16.3 统一 Message Header

``` cpp
struct MessageHeader {
    uint64_t system_boot_id;
    uint64_t px4_boot_id;       // 对飞控相关状态/动作必填；其他消息显式标记不适用
    uint64_t clock_id;          // 实际部署使用有版本的时钟域标识
    uint64_t mission_epoch;
    uint64_t localization_epoch;
    uint64_t control_epoch;

    uint64_t sequence_id;

    uint64_t capture_timestamp_ns;
    uint64_t receive_timestamp_ns;
    uint64_t publish_timestamp_ns;

    uint32_t source_id;
    uint32_t schema_version;
    uint64_t sync_generation;   // 跨设备映射代际
    uint64_t timestamp_uncertainty_ns;
    bool sync_valid;
    bool quarantine;

    bool valid;
};
```

### 16.3.1 异步处理规则

-   采集端在数据进入异步队列时绑定当前 epoch。
-   推理输出必须复制输入消息的 header，禁止在推理结束时读取"当前
    epoch"覆盖旧 epoch。
-   消费端必须检查 Boot/Mission/Localization/Control 标识。
-   碰撞事件触发后清空旧队列。
-   无法取消的 NPU 推理可以继续完成，但结果必须被拒绝。
-   任何消息不得因为"刚刚处理完成"而自动变成新鲜消息。
-   消息的 `capture_timestamp` 必须用于年龄判断。
-   若碰撞事件时间存在不确定区间，落在该区间的图像和状态一律进入
    quarantine，不用于重新定位。

### 16.3.2 时钟、飞控重启与输入溯源

时间戳只有在同一 `clock_id` 或有效映射到当前 Companion monotonic 域后才能比较；映射要包含 offset、漂移、误差界、有效期与 `sync_generation`。无法证明采集年龄时标 UNKNOWN 并拒绝依赖该新鲜度的融合/动作，不能用刚收到的时间替代采集时刻。比较年龄采用包含误差界的最坏年龄。

PX4 单独重启/重新连接导致 boot-time 回退或身份不连续时，生成新 `px4_boot_id`，作废时间映射、PX4 状态缓存、动作和在途推理，递增 localization/control epoch，退出正常控制并重新验证模式和健康状态。不能只依赖 RK3576 的 boot ID。

动作必须带 `clock_id`、`px4_boot_id`、`sync_generation`、`observation_id`、输入采集时间范围与最早安全截止时间；所有输入分别保留年龄/有效性。Epoch、时间域与源头时间不能由 Sender 补写成当前值。Header 中接收/发布时刻可随派生消息更新，但原采集时刻和上下文必须保留。

## 16.4 Epoch 更新原子操作

碰撞事件处理必须由一个原子化的状态转换函数完成：

``` python
def on_impact(event):
    lock_control_transition()

    old_localization_epoch = current_localization_epoch
    old_control_epoch = current_control_epoch

    current_localization_epoch += 1
    current_control_epoch += 1

    revoke_actions(
        localization_epoch=old_localization_epoch,
        control_epoch=old_control_epoch
    )

    flush_queues(
        older_than_localization_epoch=current_localization_epoch
    )

    # 只原子交换有效代际/引用；不得在发送锁内等待 NPU 或阻塞清理。
    invalidate_tracker_generation()
    invalidate_student_state_generation()
    reset_previous_action()

    latch_impact_event(event)
    request_control_owner_handover("IMPACT_RECOVERY")  # pending，非 PX4 已确认

    unlock_control_transition()
```

实际实现必须保证： - Epoch 递增与旧动作撤销之间不存在可执行窗口； -
发送线程在最终发送前再次校验 epoch； -
任何旧消息都不能通过重新包装绕过检查； -
控制所有权切换具有确认状态和超时分支。

本地所有权先进入 PENDING，只有 pending owner 的经校验预发送动作可通过 Gateway；模式 ACK（如协议支持）和实际飞控状态确认后才进入 ACTIVE。预发送 setpoint 也可能被仍在 Offboard 的飞控立即执行，必须按可执行动作验收。最终校验、串口入队与切换使用同一仲裁屏障，并限制串口/驱动排队深度；已经上线路的字节不能撤回，需测量在途延迟并纳入包络。队列清理与隐藏状态释放可延后，旧代际始终不可读取；重置失败保持禁止放行。

## 16.6 Action Envelope 与 TTL

所有可执行动作都必须包装在 `ActionEnvelope` 中。

``` python
ActionEnvelope = {
    "header": None,             # 含 clock_id / px4_boot_id / sync_generation
    "observation_id": None,
    "input_capture_interval_ns": None,
    "earliest_input_safe_deadline_ns": None,

    "action_id": None,
    "action_type": None,
    "coordinate_frame": None,
    "units": None,

    "issued_at_monotonic_ns": None,
    "expires_at_monotonic_ns": None,
    "max_age_ms": None,

    "sequence_id": None,
    "source": None,             # STUDENT / RECOVERY / SAFETY
    "policy_version": None,

    "payload": None,
    "validity_mask": None,
}
```

### TTL 规则

1.  `issued_at` 和 `expires_at` 使用同一个单调时钟域。
2.  发送线程不能刷新 `issued_at`。
3.  重发同一个动作不能延长 TTL。
4.  有效区间为 `issued_at <= now < expires_at`；`now >= expires_at` 必须拒绝，到期恰好相等也无效。
5.  新动作接纳时，序列号按 `(boot_id, control_epoch, source)` 严格递增；同一已接纳动作可在有效期内由 Sender 重发，但 action_id、payload 摘要、源头时间与上下文必须完全相同，且必须仍为当前缓存动作。重发不作为新接纳，不递增原动作序号；不同内容的相同序号、乱序动作与已被新动作替换的旧动作均拒绝。
6.  Epoch 不匹配必须拒绝。
7.  发送前再次检查 TTL、Epoch、控制所有权和 PX4 状态。
8.  发送队列使用 latest-valid 策略，不积压执行历史动作。
9.  Safety Controller 产生的新动作必须有独立 source、sequence 和 TTL。
10. 没有新鲜动作时，不得继续发送旧 Student 设定值。

TTL 起点与 Observation 采集时间必须分开。动作生成时不得仅从推理完成时重新计算全部有效期：`expires_at = min(issued_at + action_ttl, earliest_input_safe_deadline)`，后者由各必需输入的采集时刻、最大允许年龄和时钟误差界决定。否则旧图像经过慢推理后仍会生成“新鲜动作”。

TTL 选取原则（以下保守预算使用同一输入到执行时间口径，必须和输入截止时间共同满足）：

\[ T_{\mathrm{TTL}} >
T_{\mathrm{pipeline,P99}}+T_{\mathrm{transport,jitter}}+T_{\mathrm{margin}}
\]

同时必须满足：

\[ T_{\mathrm{TTL}} <
T_{\mathrm{maximum\ safe\ stale\ command}} \]

若不存在同时满足两式的可行区间，说明系统延迟和控制风险不匹配，必须降低模型延迟或重新设计控制架构。

## 16.7 MAVLink Offboard 发送合同

本项目当前基线是 MAVLink2 over UART。

PX4 v1.16 官方文档指出： - MAVLink Offboard setpoint
消息既承载设定值，也承载外部控制存活信号； - 需要持续超过 2Hz
的消息流； - 切入 Offboard 前需提前发送超过 1 秒； - 停止消息后，PX4 按
`COM_OF_LOSS_T` 和 `COM_OBL_RC_ACT` 执行失联处理。

因此：

-   2Hz 是官方文档的最低存活要求，不是本项目控制循环设计目标；
-   本项目实际 setpoint 频率根据控制带宽、飞控响应和通信负载测试确定；
-   当 Student 动作过期，发送线程不能继续重发旧 setpoint；
-   若 Recovery Controller
    产生了新的、合法且未过期的恢复动作，可以继续发送该新动作；
-   若无任何有效动作，必须执行预先验证的模式交接或停止 setpoint 流，让
    PX4 按配置触发 failsafe；
-   停止发送并不意味着 PX4 立即清除最后一个 setpoint；在 Offboard Loss
    超时触发前，飞控可能仍处于 Offboard 控制链路中；
-   必须把"最后一条有效动作年龄 + `COM_OF_LOSS_T` +
    实际模式交接时间"作为总陈旧指令暴露时间预算；
-   该总时间必须小于经风险评估得到的最大安全响应时间；
-   不能使用独立软件 heartbeat 掩盖实际 setpoint 已过期；
-   PX4 failsafe 参数必须和真实飞行时是否存在
    RC、位置/速度/高度状态共同测试。

setpoint 消息不是 COMMAND_LONG 命令，不能要求每包 COMMAND_ACK。发送成功只表示本地写入；用飞控日志、目标回显（如实际固件支持）、模式和响应验证接收/执行。`time_boot_ms` 不携带本地 TTL，也不能据此假设 PX4 会拒绝陈旧包；串口排队、在途包和飞控保留设定值需独立测试。

## 16.8 控制所有权（Control Ownership）

任何时刻只能有一个模块拥有 PX4 外部动作发布权：

``` text
STUDENT
   |
   | impact / invalid state / task abort
   v
IMPACT_RECOVERY
   |
   | recovery controller failure / timeout
   v
SAFETY_SUPERVISOR
   |
   | explicit mode handover or stop setpoint
   v
PX4_CONFIGURED_FAILSAFE
```

禁止： - Student 和 Recovery 同时发布； - Recovery 和 Safety
同时发布； - 旧控制所有者在交接后继续发包； - 控制所有权变化但
`control_epoch` 不变化； - 通过两个独立 MAVLink 线程绕过 Action
Validator。

## 16.9 PX4 Interface

PX4 Interface 负责：

-   MAVLink2 连接；
-   心跳与状态接收；
-   姿态和角速度接收；
-   EKF2 状态和 reset counter；
-   `v_xy_valid` / `v_z_valid`；
-   高度和位置有效性；
-   高层 setpoint 映射；
-   控制模式请求；
-   命令 ACK；
-   Offboard 状态监测；
-   failsafe 状态监测；
-   参数快照和固件版本记录。

`v_xy_valid` / `v_z_valid` 等是项目内部归一化状态名，不代表标准 MAVLink 速度消息原生具有这些字段。必须列出实际固件可获取的消息、估计健康位、时间戳、重置计数与逐轴有效性映射，核对源代码并做故障注入；仅有有限速度数值不能置为有效，未获得可信映射时标 UNKNOWN 并拒绝相应动作。

感知、任务和 RL 模块不得直接依赖 UART 实现。

# 17. 安全架构与故障处理

## 17.1 安全分层

  ---------------------------------------------------------------------------------------------
  层级                    组成                    职责
  ----------------------- ----------------------- ---------------------------------------------
  L1                      PX4                     姿态/角速度内环、控制分配、飞控侧 failsafe

  L2                      Independent E-stop      规则要求的紧急停桨遥控器/接收机和安全员

  L3                      RK3576 Safety           状态有效性、动作 TTL、限幅、控制权管理
                          Supervisor

  L4                      Mission Recovery        定位失效、任务失败、视觉重新获取、返库/退出

## 17.3 Safety Supervisor 动作检查顺序

每条动作发布前必须依次检查：

1.  `system_boot_id` 匹配；
2.  `mission_epoch` 匹配；
3.  `localization_epoch` 匹配；
4.  `control_epoch` 匹配；
5.  动作来源拥有当前控制权；
6.  `sequence_id` 合法；
7.  TTL 未过期；
8.  输入数据年龄在允许范围；
9.  所需估计状态有效；
10. 坐标系和单位符合 Schema；
11. 数值有限；
12. 速度/姿态/推力限制通过；
13. 传感器和 PX4 健康状态通过；
14. 任务状态允许该动作；
15. 最终发送前再次执行 Epoch 和 TTL 检查。

任何一项失败都必须拒绝动作并记录原因码。

## 17.4 PX4 Failsafe 配置管理

PX4 参数不是在文档中写一个推荐数值就算完成。必须保存：

-   固件版本和 commit；
-   参数全量导出；
-   参数变更记录；
-   QGroundControl 参数截图或导出；
-   Offboard Loss 测试记录；
-   Position Loss 测试记录；
-   RC Loss 测试记录；
-   无 RC 输入测试记录；
-   位置、速度、高度各状态失效测试记录。

重点参数包括：

-   `COM_OF_LOSS_T`
-   `COM_OBL_RC_ACT`
-   `COM_POSCTL_NAVL`
-   `COM_RC_IN_MODE`
-   `COM_RCL_EXCEPT`
-   相关 EKF2 传感器融合和有效性参数。

必须分别验证 Offboard Loss 与 Position Loss，不能认为它们是同一事件。

## 17.5 碰撞后特别禁止事项

-   不允许继续使用碰撞前 Position Setpoint。
-   不允许把旧 Local Position 当作当前真实位置。
-   不允许继续使用碰撞前速度积分。
-   不允许继续沿旧地图路径盲目飞行。
-   不允许将碰撞前 GRU 状态传给恢复阶段。
-   不允许重发过期动作。
-   不允许旧 epoch 结果回流。
-   不允许粗略视觉方位直接生成速度闭环命令。
-   不允许把 Attitude + Thrust 解释为自动悬停。
-   不允许视觉重新获取失败后自动恢复原任务。

### 20.11.1 测试数据分层

所有性能测试至少区分：

-   In-domain；
-   Held-out visual domain；
-   Dynamic-object domain；
-   Sensor-degraded domain；
-   Lab-rig domain；
-   Post-impact domain；
-   Real-arena domain（若可进入正式场地）。

不得把同一背景连续视频随机拆帧后，作为独立训练集和测试集。测试集应按采集批次、背景、光照或场景进行隔离。

### 20.11.2 失败处理

-   合同错误：停止 Gate，修复后从失败用例和完整回归集重新测试。
-   性能不达标：定位失败场景，更新模型/控制器后重新运行完整评估集。
-   测试设备异常：本轮结果标记为 INVALID，不得计入 PASS。
-   样本量不足：标记 INCOMPLETE，不得用少量成功案例替代统计结果。

### 20.11.3 统计结论边界

零错误是指定样本与故障域内的观测结果，不是对任意时序的数学保证。报告成功率置信区间、每个分层的样本数、失败/超时/安全退出/invalid 分母与随机 seed；不能删除失败后重试替代原结果。高度相关的连续帧不能当成独立重复试验。门槛、样本量和分层在正式测试前冻结，修改后更换评价版本，保留旧结果。

碰撞后的安全退出率与恢复后继续任务率分开；触点通电、停靠、数据完整性与充电互锁分别统计。

### 20.12.1 对建议门槛的限制

-   检测指标必须按场景分层，不能用总体平均值掩盖某类目标失效。
-   地标误匹配比漏检更危险；宁可输出"未知"，也不能错误地高置信度选中一个区域。
-   视觉重新获取失败可以接受，但必须进入安全退出；错误地把旧位置当成新位置不可接受。
-   机库停靠成功率不代表触点电气可靠性，二者分别验收。
-   P99 延迟不能代替最大延迟和连续超时测试。
-   任何建议门槛若与实际规则、物理边界或风险分析冲突，应提高安全要求，不得为追求
    PASS 而降低标准。

# 26. FLIGHT_CONTROL_CONTRACT：飞控与恢复控制合同

## 26.1 目的

本章将 PX4 与 RK3576 之间的控制边界变成可测试合同。该合同优先于普通
Skill 对 PX4 的直接调用。

## 26.2 控制层级

``` text
Mission / Behavior Tree
          |
          v
Student or Recovery Controller
          |
          v
Action Envelope
          |
          v
Action Validator
          |
          v
Safety Supervisor
          |
          v
Single PX4 Command Gateway
          |
          v
MAVLink2 / PX4
          |
          v
Attitude / Rate / Control Allocation
          |
          v
ESC / Motors
```

只有 `Single PX4 Command Gateway` 可以发送飞行控制 setpoint。

## 26.3 正常控制合同

正常导航采用高层航向对齐机体系速度动作：

-   策略输出 BODY_HEADING_FLU；
-   PX4 Adapter 转换为所需 MAVLink/PX4 坐标；
-   水平速度控制要求对应速度估计有效；
-   垂直速度控制要求对应垂直速度估计有效；
-   姿态和角速度状态必须有效；
-   任何所需状态无效时拒绝对应动作；
-   不得通过输出零速度掩盖估计失效。

项目当前候选 MAVLink 消息为 `SET_POSITION_TARGET_LOCAL_NED`，使用
`MAV_FRAME_LOCAL_NED`。策略层 BODY_HEADING_FLU 的速度向量由 PX4 Adapter
根据有效 yaw 转换为 NED，再发送给 PX4。

全轴速度 + yaw-rate 候选 `type_mask=1479`；不控制垂直速度时候选
`type_mask=1511`，在第 10.4.3 节垂直完整性验证通过前禁止使用。掩码位定义和计算见第 10.4.1 节。PX4 v1.16
文档列出了多旋翼支持的 LOCAL_NED 和 BODY_NED 速度设定，但本项目选择
LOCAL_NED，以避免把 yaw-aligned body frame
与完整倾斜机体系混淆。最终消息字段和掩码仍需在实际固件上验证。

## 26.4 碰撞恢复控制合同

恢复期间采用独立动作类型：

-   普通 Student 速度动作全部撤销；
-   Recovery Controller 成为唯一外部控制所有者；
-   先检查姿态和角速度；
-   姿态控制不等于位置控制；
-   Attitude + Thrust 不等于定高；
-   垂直闭环必须重新确认高度/测距状态；
-   视觉粗略方位不等于速度估计；
-   视觉粗略方位阶段禁止水平平移；
-   只有经过专门验证的 IBVS 才能进入局部视觉伺服；
-   恢复超时或控制状态不满足时，进入已验证 PX4 failsafe。

## 27.2 过期与异步消息消费规则

消息消费者统一执行：

``` python
def validate_message(msg, current_context, now_ns):
    if msg.system_boot_id != current_context.system_boot_id:
        return "REJECT_BOOT_MISMATCH"

    if msg.mission_epoch != current_context.mission_epoch:
        return "REJECT_MISSION_EPOCH"

    if msg.localization_epoch != current_context.localization_epoch:
        return "REJECT_LOCALIZATION_EPOCH"

    if msg.control_epoch != current_context.control_epoch:
        return "REJECT_CONTROL_EPOCH"

    if msg.clock_id != current_context.clock_id:
        return "REJECT_CLOCK_DOMAIN"  # 映射须在进入本函数前验证

    if not sync_and_px4_boot_valid(msg, current_context):
        return "REJECT_SYNC_OR_PX4_BOOT"

    if msg.quarantine:
        return "REJECT_QUARANTINE"

    if msg.capture_timestamp_ns > now_ns:
        return "REJECT_FUTURE_TIMESTAMP"

    if now_ns - msg.capture_timestamp_ns > allowed_age_ns(msg.source_id):
        return "REJECT_STALE"

    if not msg.valid:
        return "REJECT_INVALID"

    return "ACCEPT"
```

以上仍为非可执行伪代码。实际实现还需类型/Schema、时间误差界、事件时间区间、消息源有效性与序号检查；`control_epoch`、时钟域和 quarantine 均为必检项。

## 27.3 Action 发送前的最后一道校验

``` python
def validate_action(action, context, now_ns, *, stage):
    assert action.system_boot_id == context.system_boot_id
    assert action.mission_epoch == context.mission_epoch
    assert action.localization_epoch == context.localization_epoch
    assert action.control_epoch == context.control_epoch

    assert stage in ("ADMIT_NEW", "SEND_CACHED")
    if stage == "ADMIT_NEW":
        assert action.sequence_id > context.last_accepted_sequence
    else:
        # 当前缓存动作首发/重发：精确匹配身份、上下文、内容和原期限。
        assert immutable_identity_and_digest(action) == context.cached_action_identity
    assert action.issued_at_monotonic_ns <= now_ns
    assert now_ns < action.expires_at_monotonic_ns

    assert action.clock_id == context.clock_id
    assert action.px4_boot_id == context.px4_boot_id
    assert input_provenance_and_deadlines_valid(action, context, now_ns)
    assert action.source == context.current_control_owner
    assert all_values_finite(action.payload)
    assert coordinate_frame_supported(action)
    assert required_estimates_valid(action, context.px4_state)
    assert safety_limits_pass(action, context)

    return True
```

以上为合同伪代码，不是现有入口。生产代码不能只使用 `assert`，必须返回明确错误码、计数和日志。ADMIT_NEW 成功后的序号/缓存提交须在仲裁屏障内完成；SEND_CACHED 每次都重新检查状态、权限、TTL 和输入截止时间，但不更新动作的原时间与序号。

## 27.4 MAVLink Sender 的关键要求

Sender 线程只负责发送已经通过校验的最新动作：

-   将 Action Envelope 的本地 monotonic 时间与 PX4 boot-time
    映射分开处理；
-   `time_boot_ms` 必须按 PX4 boot-time 生成，TTL 仍按 RK3576 monotonic
    clock 检查；
-   不缓存过期动作；
-   不因定时器触发而重发已过期动作；
-   不自行生成新的 `issued_at`；
-   不自行修改 Epoch；
-   不自行改变动作来源；
-   不在 Student 卡住时伪造 Student 健康；
-   不允许多个线程同时发送控制 setpoint。

若动作过期：

1.  立即标记 `ACTION_EXPIRED`；
2.  撤销该动作；
3.  通知 Safety Supervisor；
4.  由当前安全策略决定是否切换控制所有者；
5.  若没有有效外部控制动作，则停止旧 MAVLink setpoint
    流或执行已验证模式切换；
6.  PX4 按实际固件和参数触发对应 failsafe。

## 27.5 Action TTL 参数冻结方法

TTL 不使用随意指定的常数。

先测量：

-   相机采集到消息可用延迟；
-   视觉推理延迟；
-   状态融合延迟；
-   Student 推理延迟；
-   Safety Supervisor 延迟；
-   UART/MAVLink 发送延迟；
-   PX4 收到并处理设定值延迟。

然后确定：

-   `pipeline_latency_p99`；
-   `transport_jitter_p99`；
-   `max_safe_stale_action_time`；
-   `watchdog_timeout`；
-   `COM_OF_LOSS_T`。

必须同时计算 PX4 端的陈旧 setpoint 暴露时间：

\[ T_{stale,total} = T_{last_action_age} + T_{COM_OF_LOSS_T} +
T_{mode_transition} \]

若 Safety Supervisor
能生成新的有效安全动作，则该动作可替换旧动作，但仍必须满足自己的 TTL
和控制所有权合同。若不能生成新动作，PX4 端的最后 setpoint
保留时间必须计入安全预算。

只有当 TTL、watchdog、`COM_OF_LOSS_T`
和模式交接时间之间存在明确且可验证的时间关系，才能冻结参数。

## 27.6 坐标系单元测试

必须验证：

  输入动作                   预期机体运动方向
  -------------------------- ------------------------------------
  `vx_forward > 0`           前进
  `vy_left > 0`              左移
  `vz_up > 0`                上升
  `yaw_rate_ccw_world > 0`   绕世界 Up 轴、从上方观察逆时针偏航
  全零且速度估计有效         速度控制器接收零速度设定值
  速度估计无效               动作被拒绝，不发送速度设定值

同时验证： - BODY_HEADING_FLU 到 LOCAL_NED 的 yaw 变换； -
North/West/East/South 四个航向下的前进和左移； - `vz_up` 到 `v_D`
的符号； - yaw-rate 的 NED 符号； - 全轴速度掩码 1479； -
忽略垂直速度掩码 1511； - NaN/忽略字段； - MAVLink 发送与 PX4 实际状态。
